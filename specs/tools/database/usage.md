# Database MCP routing

**Trigger:** Database inspection, write or migration validation.

Use one compatible MCP only for database projects: DBHub is the first candidate, Toolbox an alternative. Confirm source/environment/schema/permissions before querying; inspect related structure, bound columns/conditions/results, prefer parameter binding and validate dynamic identifiers. Development/test DML within existing authorization does not require approval per statement. Writes need bounded selection/expected affected rows and readback; SELECT max_rows does not bound DML. DDL/history repairs use reviewed project migrations/TDD. Verify single-call transaction behavior per engine; never assume BEGIN and COMMIT across calls share a session. Timeout/cancel/transport loss means outcome may be unknown: inspect idempotency keys/records/migration history before retry. Rollback applies to uncommitted work; committed recovery uses compensation/migrations. Use database-account permissions, not MCP readOnlyHint, as the access boundary. Credentials are local references. Installation/handshake/schema/read/write are separately evidenced in isolated fixtures before real write use.

Verified adapter: DBHub 1.5.0 supports `readonly` for built-in and custom tools; custom value parameters use PostgreSQL `$1` or MySQL `?`. Result counts are `statements[].count`. PostgreSQL 17.11 and MySQL 8.4.11 passed isolated schema/read/parameterized-write/permission/commit/rollback checks. A MySQL write batch containing `SLEEP` returned success and committed despite its configured one-second query budget; a PostgreSQL batch returned a tool error with no commit visible to an independent reader. Neither result establishes a universal cancellation guarantee. Always reconcile writes before retrying.
